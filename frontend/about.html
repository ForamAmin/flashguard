What FlashGuard actually is

FlashGuard is not a ticketing platform. It's infrastructure a real platform integrates for one specific moment: the instant a limited number of slots go live and everyone tries to claim one at once. The integrating platform — we call it "Jalsa" throughout this project — keeps its own users, payments, and order flow. FlashGuard owns exactly one thing, correctly: who gets a slot, and who doesn't, under real concurrent load.

Who owns what

FlashGuard owns

  • Organizations and API credentials
  • Drops — the limited-slot inventory itself
  • Claim concurrency and correctness
  • The full claim audit trail
  • Overselling prevention

The integrating platform owns

  • End customers and their accounts
  • The website and checkout experience
  • Payments and order processing
  • Ticket delivery and notifications

The problem, in one line

Checking "is inventory above zero" and then decrementing it are two separate steps. Under concurrency, two requests can both check, both see room, and both decrement — selling more than exists. This isn't rare under real load; it's the default outcome of doing it naively.

FlashGuard closes that gap by making the check and the decrement a single, indivisible operation inside Redis — there's no gap in the middle for a second request to slip through.

What happens when you press "Claim"

01

Authenticate

The request's API key is hashed and matched to an organization. No raw key is ever stored — only its hash.

02

Confirm ownership

The drop being claimed is checked against the calling organization. A mismatch returns the same "not found" response a nonexistent drop would — never confirming another tenant's data exists.

03

Ask Redis, atomically

A Lua script checks the live counter and decrements it in one indivisible step. This is the only place concurrency is actually resolved.

04

Record the outcome

Whether the claim succeeded or the drop was already sold out, a record is written to Postgres — the durable audit trail behind every rejection-rate and throughput number.

05

Respond immediately

SUCCESS or SOLD_OUT is returned synchronously — no polling, no waiting.

Proven, not assumed

This behavior was load tested with k6: 200 concurrent virtual users firing 10,000 claim requests at a drop configured with exactly 100 slots. Result: exactly 100 successful claims, 9,900 correctly rejected, and Redis inventory landing on zero — never negative. See it happen in real time on the live drops page.

Built with Spring Boot, PostgreSQL, and Redis. Load tested with k6.
